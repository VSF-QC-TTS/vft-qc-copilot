## Existing Backend Runner Endpoints

All endpoints below require the runner service token and Spring role `RUNNER`.

User JWTs cannot call `/internal/runner/**`. Runner tokens cannot call frontend `/api/**`.

```text
POST /internal/runner/instances/register
POST /internal/runner/instances/heartbeat
GET  /internal/runner/test-runs/{testRunId}/config
POST /internal/runner/test-runs/{testRunId}/runtime-secrets
GET  /internal/runner/test-runs/{testRunId}/control-state
POST /internal/runner/events
```

The public UI SSE endpoint is not called by the runner, but it consumes the same persisted runner events:

```text

```

## Redis Command Contract

Backend publishes compact commands to Redis stream:

```text
vfqc:runs:commands
```

Backend event consumer reads compact runner events from:

```text
vfqc:runs:events
```

Implementation note checked against backend code on 2026-07-09:

```text
RunnerRedisEventConsumerImpl reads vfqc:runs:events with consumer group vfqc-api
and consumer name api-runner-events. It maps Redis fields to RunnerEventRequest
and has retry/DLQ behavior. RunnerRedisEventConsumerScheduler can poll it in
production when vfqc.runner.redis-events.enabled=true. This scheduler is disabled
by default, so keep HTTP event ingestion as the standalone runner default unless
Redis event output is explicitly enabled and operated.
```

DLQ streams:

```text
vfqc:runs:commands:dlq
vfqc:runs:events:dlq
```

Command payload shape published by backend:

```ts
export interface RunnerCommandMessage {
  commandId: string; // UUID
  testRunId: string; // UUID
  commandType: "START_RUN" | "CANCEL_RUN";
  createdAt: string; // ISO offset date-time
}
```

Rules:

- Redis payloads contain references only.
- Do not put plaintext secrets, dataset rows, full target configs, raw responses, full Promptfoo configs, or artifact contents into Redis.
- Backend marks commands as `PUBLISHED` after stream publish.
- Runner should treat `START_RUN` as the trigger to fetch locked config from backend.
- Runner should treat `CANCEL_RUN` and control-state polling as best-effort cancellation signals.

### RunnerTestRunConfigResponse

Response body for:

```text
GET /internal/runner/test-runs/{testRunId}/config
```

Supports Spring pageable query params. Default backend page size is 100 rows:

```text
?page=0&size=100
```

```ts
export interface RunnerTestRunConfigResponse {
  testRunId: string; // UUID
  projectId: string; // UUID
  runType: TestRunType;
  status: TestRunStatus;
  datasetId: string; // UUID
  datasetVersionId: string; // UUID
  datasetSchemaId: string; // UUID
  datasetSchemaVersion: number;
  progressTotal: number;
  domainSnapshot: Record<string, unknown>;
  promptfooSnapshot: Record<string, unknown>;
  targets: TargetSnapshot[];
  evaluators: EvaluatorSnapshot[];
  rows: DatasetRowSnapshot[];
}

export interface TargetSnapshot {
  id: string; // UUID, this is testRunTargetId used by result events
  targetType: TestRunTargetType;
  chatbotTargetId?: string | null; // UUID
  providerId?: string | null; // UUID
  model?: string | null;
  name: string;
  orderIndex: number;
  config: Record<string, unknown>; // locked sanitized target config; may contain secret references, not plaintext
}

export interface EvaluatorSnapshot {
  id: number; // test_run_evaluator_versions row id
  evaluatorId: string; // UUID
  evaluatorVersionId: string; // UUID
  evaluatorType: string;
  version: number;
  orderIndex: number;
  config: Record<string, unknown>;
  rules: Array<Record<string, unknown>>;
}

export interface DatasetRowSnapshot {
  id: number; // datasetRowId used by result events
  rowIndex: number;
  cells: Record<string, unknown>;
  revision: number;
  rowHash: string;
}
```

Rules:

- This is locked run config. The runner must not read mutable project/target/evaluator state from normal frontend APIs.
- Config is sanitized. Plaintext secrets are excluded.
- If the run has more rows than one page, the runner must page through config rows or the backend needs a dedicated row-page contract. Current DTO returns rows in the config response.
- `TargetSnapshot.id` and `DatasetRowSnapshot.id` are required when sending testcase result events.
- `promptfooSnapshot` exists, but the runner adapter is still responsible for converting the locked backend domain shape into a concrete Promptfoo config file.

### RunnerEventRequest

Request body for:

```text
POST /internal/runner/events
```

```ts
export interface RunnerEventRequest {
  eventId: string; // required, runner-generated idempotency id
  testRunId: string; // UUID, required
  eventType: RunnerEventType; // required
  runnerId?: string | null; // UUID, optional runner instance id
  commandId?: string | null; // UUID, optional command id
  occurredAt?: string | null; // ISO offset date-time
  payload?: Record<string, unknown> | null;
}
```

Rules:

- `eventId` is globally idempotent. Re-sending the exact same `eventId`, `testRunId`, and `eventType` returns the existing sequence. Reusing `eventId` with different metadata is a conflict.
- Backend sanitizes payload before persistence, but runner must still sanitize before sending.
- Backend assigns per-run `sequenceNo`.
- Backend persists `RunnerEvent` before SSE broadcast.

Implementation note:

- `RunnerEventStatus` includes `DUPLICATE`, but current `RunnerEventIngestionServiceImpl` returns the existing stored event status for exact idempotent replays, usually `APPLIED`. Runner retry logic should treat a successful replay with the same `eventId`, `testRunId`, `eventType`, and existing `sequenceNo` as success even when status is not `DUPLICATE`.

## Event Payload Shapes Expected By Current Backend

Only the keys below have backend side effects today. Extra payload keys may be persisted after sanitization, but do not rely on them for state transitions unless backend is extended.

### RUN_STARTED

Moves run from `QUEUED` to `RUNNING`.

```ts

  status?: "RUNNING";
}
```

### RUN_PROGRESS

Allowed when run is `RUNNING` or `CANCEL_REQUESTED`.

```ts
export interface RunProgressPayload {
  completed?: number;
  total?: number;
}
```

### TESTCASE_COMPLETED

Allowed when run is `RUNNING` or `CANCEL_REQUESTED`.

```ts
export interface TestcaseCompletedPayload {
  testRunTargetId: string; // UUID, required
  datasetRowId: number; // required
  status?: "PASSED" | "FAILED" | "ERROR" | "JUDGE_ERROR" | "TIMEOUT";
  score?: number | string;
  passed?: boolean;
  errorCategory?: string;
  request?: Record<string, unknown>;
  response?: Record<string, unknown>;
  extractedOutput?: Record<string, unknown>;
  gradingResult?: Record<string, unknown>;
  componentResults?: Record<string, unknown>;
  tokenUsage?: Record<string, unknown>;
  latencyMs?: number | string;
  machineSummary?: string;
}
```

Backend behavior:

- Upserts by `(testRunId, testRunTargetId, datasetRowId)`.
- If `status` is omitted, default for `TESTCASE_COMPLETED` is `PASSED`.
- `FAILED` means business/evaluator failure, not system failure.
- `request`, `response`, and `machineSummary` are sanitized before persistence.

### TESTCASE_ERROR

Same shape as `TESTCASE_COMPLETED`.

Backend behavior:

- If `status` is omitted, default is `ERROR`.
- Use for execution/evaluator errors for a single row/target.

## SSE Projection DTO

Frontend subscribers receive projected events from:

```text
GET /api/v1/test-runs/{testRunId}/events
```

Java record:

```ts
export interface TestRunSseEventResponse {
  eventId: string;
  sequenceNo: number;
  testRunId: string; // UUID
  eventType: RunnerEventType;
  occurredAt?: string | null; // ISO offset date-time
  createdAt: string; // ISO offset date-time
  payload: Record<string, unknown>;
}
```

Projection rules:

- SSE event id equals `runner_events.sequence_no`.
- SSE event name equals `RunnerEventType`.
- `Last-Event-ID` replays events after the given sequence.
- Replay without cursor is capped.
- SSE strips large/raw unsafe fields such as `request`, `response`, `headers`, raw body, raw cURL, runtime secrets, Promptfoo config, and artifact content.

## Runner Lifecycle To Document

Recommended lifecycle for MVP:

1. Register runner instance.
2. Send heartbeat as `IDLE`.
3. Consume `START_RUN` command from Redis.
4. Heartbeat as `BUSY` with `currentCommandId` and `currentTestRunId`.
5. Fetch locked config from `GET /internal/runner/test-runs/{testRunId}/config`.
6. Extract referenced secret ids from locked target/provider/evaluator configs.
7. Resolve runtime secrets through `POST /runtime-secrets`.
8. Build Promptfoo config in a temp working directory.
9. Send `RUN_STARTED`.
10. Run Promptfoo.
11. For each testcase result, send `TESTCASE_COMPLETED` or `TESTCASE_ERROR`.
12. Send `RUN_PROGRESS` periodically.
13. Poll control state during execution.
14. On graceful cancellation, stop Promptfoo and send `RUN_CANCELLED`.
15. On successful completion, send `RUN_COMPLETED`.
16. On system failure, send `RUN_FAILED`.
17. Heartbeat as `IDLE`.

## Security And Sanitization Requirements

- Runtime secrets are memory-only.
- Never log plaintext secrets, bearer tokens, cookies, raw external payloads, raw Promptfoo config, raw target responses, or runtime secret bundles.
- Never put full config, full rows, raw response bodies, artifact content, or secrets into Redis.
- Promptfoo config artifacts must be sanitized before any future artifact upload/download feature.
- Runner event payloads must be sanitized before send; backend also sanitizes before persistence.
- `TESTCASE_COMPLETED` payload may include request/response for result detail, but it must not include plaintext tokens or secret values.

## Current Backend Gaps For Full Runner Docs

Document these as known gaps, not as implemented behavior:

- No dedicated backend artifact upload/metadata endpoint is currently implemented.
- No explicit command acknowledgement endpoint is currently implemented, despite command status enum containing `ACKNOWLEDGED`.
- Redis command consumer for the standalone runner is not implemented in this repository yet.
- Exact Promptfoo adapter schema is not finalized. Backend stores `promptfooSnapshot`, but runner must still map locked VFQC domain snapshots to executable Promptfoo config.
- Large dataset row paging may need a more explicit runner row-page contract if a run exceeds one config page.
